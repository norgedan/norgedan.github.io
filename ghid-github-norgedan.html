CAPITOLUL II

Cum funcționează GitHub Pages — esențialul

GitHub Pages transformă automat un repository în site web public. Nu ai nevoie de server, de hosting plătit sau de configurare complicată. Regula este simplă: orice fișier HTML din repository-ul norgedan.github.io devine accesibil la URL-ul corespunzător.

REGULA DE AUR

corpus3/ro/1-romania-si-rusia-ro.html din repo → https://norgedan.github.io/corpus3/ro/1-romania-si-rusia-ro.html pe internet. Structura de foldere devine structura URL-urilor.

Ciclul complet de la editare la publicare

1
Editezi local

Modifici un fișier pe mașina ta — cu orice editor de text, sau cu Claude care îți generează fișierul.

2
git add

Marchezi fișierele modificate pentru commit. git add fisier.html sau git add . pentru tot.

3
git commit

Creezi un punct de salvare cu un mesaj descriptiv. Acesta este istoria proiectului tău — fiecare commit este un moment la care poți reveni.

4
git push

Trimiți modificările pe GitHub. De aici, GitHub Pages preia automat și publică în 1-3 minute.

5
Ctrl+Shift+R

Hard refresh în browser pentru a evita cache-ul local. Modificările sunt live.

# Secvența completă — de fiecare dată
cd ~/norgedan.github.io
git add fisier-modificat.html
git commit -m "Descriere scurtă a ce ai schimbat"
git push origin main
CAPITOLUL III

Modelul chirurgical — editare precisă, fără risc

„Chirurgical" înseamnă că modifici exact ce trebuie, nimic mai mult, și că orice greșeală poate fi reparată. Git este sistemul de siguranță perfect — păstrează întreaga istorie și permite revenirea la orice moment anterior.

Adaugi un fișier nou

# Copiezi fișierul generat în locul corect
cp ~/Downloads/document-nou.html ~/norgedan.github.io/corpus3/ro/
git add corpus3/ro/document-nou.html
git commit -m "Add: document nou despre X"
git push origin main

Modifici un fișier existent

# Înlocuiești fișierul cu versiunea nouă
cp ~/Downloads/index-actualizat.html ~/norgedan.github.io/index.html
git add index.html
git commit -m "Update: index.html — adăugat Corpus IV"
git push origin main

Ștergi un fișier

# git rm îl șterge și din repo
git rm corpus3/ro/document-de-sters.html
git commit -m "Remove: document eliminat — motiv"
git push origin main

Adaugi un folder întreg

# Copiezi tot folderul
cp -r ~/Downloads/corpus4 ~/norgedan.github.io/
git add corpus4/
git commit -m "Add: Corpus IV — descriere"
git push origin main

Revii la o versiune anterioară

# Vezi istoricul
git log --oneline -10
e72a90a Force redeploy
0f0ac7e Update README
768cb85 Add Corpus III to main index
6b12b80 Add Corpus III

# Recuperezi un fișier dintr-un commit anterior
git checkout 768cb85 -- index.html
git commit -m "Restore: index.html din versiunea anterioară"
git push origin main
SIGURANȚA ABSOLUTĂ A MODELULUI

Nicio greșeală nu este permanentă în git. Orice fișier șters poate fi recuperat, orice versiune poate fi restaurată. Acesta este motivul pentru care mesajele de commit clare sunt esențiale — ele sunt harta cu care navighezi în istoric.

Aplicarea unui patch primit — cu dovadă, nu din ochi

Modelul folosit din 27 septembrie: fiecare fișier primit vine cu dimensiunea, hash-ul lui și hash-urile git așteptate. Comparația cifrelor înlocuiește încrederea.

# 1. fișierul descărcat e cel corect?
ls -la ~/Downloads/pas3-corpus.patch
sha256 ~/Downloads/pas3-corpus.patch     # comparat cu valoarea dată

# 2. se aplică pe starea ta? (--check nu modifică nimic)
cd ~/corpus
git fetch origin && git status -sb        # ## main...origin/main
git apply --check ~/Downloads/pas3-corpus.patch && git apply ~/Downloads/pas3-corpus.patch

# 3. rezultatul e bit cu bit cel testat?
git add -A && git diff --cached --raw    # hash vechi -> hash nou, comparate
git diff --cached                        # citit efectiv
git commit -m "mesaj clar"
git push origin main                     # garda verifică singură

Verificare înainte de push — bună practică

# Vezi ce urmează să fie trimis
git status
On branch main
Changes to be committed:
  modified: index.html
  new file: corpus3/ro/7-document-nou.html

# Vezi exact ce s-a schimbat într-un fișier
git diff index.html
CAPITOLUL IV

Document nou — procedura completă

Operațiunea cea mai frecventă. Din 27 septembrie începe într-un singur loc — manifestul — iar verificarea cere singură tot restul. Nu mai trebuie ținută minte lista; trebuie doar ca push-ul să iasă verde.

REGULA DE BAZĂ

Un document = o pereche RO+NO = un rând în scripts/documente.tsv. Fără rând, documentul nu există pentru verificare — iar un fișier de pe disc fără rând e semnalat ca necunoscut.

1
Pornește curat

Starea tuturor clonelor față de GitHub (comanda din Capitolul VII) — fiecare trebuie să fie ## main...origin/main. Golește ~/Downloads de fișierele proiectului.

2
Cele două fișiere

În repo-ul colecției, după convenția ei (Corpus I: 07-titlu-ro.html + 07-tittel-no.html; Corpus II/III: ro/ și no/). Antetul complet: title, description unică, canonical spre propriul fișier, hreflang ro / nb / x-default, og:title, og:description, og:url; <html lang="ro"> și <html lang="nb">.

3
Rândul în manifest

În norgedan.github.io/scripts/documente.tsv, separat prin TAB: id nou (nu se refolosește niciodată), colecție, repo, calea RO, calea NO, titlul RO și titlul NO — exact textul din <title>.

4
Sitemap, hub, pagina colecției

Ambele URL-uri în sitemap-ul repo-ului; cardurile RO și NO în index.html din hub; linkurile în pagina colecției.

5
Cifrele

verifica-site.sh --tablou dă numerele reale. Actualizează rândul colecției și TOTAL în tabloul din status-proiect.html, apoi orice declarație publică („6 documente”, „~58.000 de cuvinte”). Verificarea le compară pe toate cu măsurătoarea.

6
Verifică

sh ~/norgedan.github.io/scripts/verifica-site.sh — fiecare PROBLEMA spune exact ce lipsește și unde. Repari până la EXIT=0.

7
Commit în TOATE repo-urile atinse, apoi push

Un document nou atinge de obicei două repo-uri (colecția + hub-ul). Comiți în amândouă înainte de primul push; garda verifică tot site-ul și semnalează commit-urile încă nepublicate. Apoi Ctrl+Shift+R live.

VERIFICAREA NU MAI E UN PAS DE ȚINUT MINTE

Garda rulează la fiecare git push, din oricare repo. Dacă un pas a fost sărit, push-ul se oprește și spune care. Ocolirea — git push --no-verify — există, dar e o decizie conștientă, nu o scăpare (vezi Capitolul VIII).

CAPITOLUL V

Cum creezi un repository nou

Ai două opțiuni: prin interfața web GitHub (cel mai simplu) sau din terminal. Pentru conținut nou care face parte din site-ul existent — prefer folderul în norgedan.github.io. Pentru proiecte complet separate — un repo nou.

Opțiunea 1 — Folder în norgedan.github.io (recomandat pentru conținut nou)

cd ~/norgedan.github.io
mkdir -p corpus4/ro corpus4/no
# Copiezi fișierele HTML în folder
cp ~/Downloads/*.html corpus4/ro/
git add corpus4/
git commit -m "Add: Corpus IV — descriere"
git push origin main

Opțiunea 2 — Repository nou separat

1
Creează pe GitHub web

github.com → butonul verde New → nume repo → Public → bifează Add README → Create repository.

2
Activează GitHub Pages

Settings → Pages → Source: Deploy from branch → Branch: main → folder: / (root) → Save.

3
Clonează local

git clone https://github.com/norgedan/nume-repo.git — apare ca folder pe mașina ta.

4
Adaugă fișierele

Copiezi HTML-urile în folder, git add ., git commit, git push.

5
Linkează din index.html principal

Adaugi cardul în norgedan.github.io/index.html și actualizezi sitemap.xml.

ATENȚIE — REPO NOU VS FOLDER

Un repo nou separat înseamnă muncă suplimentară: GitHub Pages activat separat, URL de forma norgedan.github.io/repo-nou/ funcționează doar dacă repo-ul se numește exact cum vrei URL-ul. Folderul în norgedan.github.io este mai simplu și mai curat pentru conținut editorial.

CAPITOLUL VI

Optimizarea unui repository — lista completă

1. About — prima impresie pe GitHub

Pe pagina repo-ului, rotița ⚙️ lângă About → completezi: Description (1-2 propoziții clare), Website (URL-ul live), Topics (10 cuvinte cheie relevante).

2. README.md — documentul de bază

Fiecare repo ar trebui să aibă un README care explică: ce conține, la ce URL e live, cum este organizat. Editezi direct din GitHub web — click pe README.md → ✏️ Edit.

3. Meta tags în fiecare HTML

<!-- Esențial pentru SEO și social sharing -->
<meta name="description" content="Descriere clară, 150-160 caractere">
<meta name="keywords" content="cuvant1, cuvant2, cuvant3">
<meta property="og:title" content="Titlu pentru Facebook/LinkedIn">
<meta property="og:description" content="Descriere pentru share">
<meta property="og:url" content="https://norgedan.github.io/...">
<link rel="canonical" href="https://norgedan.github.io/...">

4. sitemap.xml — Google indexează tot

Fiecare URL nou adăugat merge și în sitemap.xml. Structura minimă:

<url>
  <loc>https://norgedan.github.io/corpus3/ro/1-romania-si-rusia-ro.html</loc>
  <priority>0.8</priority>
</url>

5. Google Search Console

Ai deja verificarea Google Search Console. Periodic intri pe search.google.com/search-console → Sitemaps → confirmi că sitemap-ul tău este indexat corect și verifici dacă există erori de crawl.

CAPITOLUL VII

Menținerea în timp — rutina corectă

Înainte de orice sesiune de lucru

# starea TUTUROR clonelor față de GitHub — fără să modifici nimic
for r in norgedan.github.io corpus corpus2 opera limba limba-ro-final; do git -C ~/$r fetch -q origin; echo "$r $(git -C ~/$r status -sb | head -1)"; done
# fiecare linie: ## main...origin/main
# [behind N] = ceva nou pe GitHub (ex. editat din browser): git -C ~/repo pull origin main

fetch doar aduce și arată; pull modifică. Întâi te uiți, apoi decizi. Cu pull.ff only (Capitolul X), un pull nu poate produce niciodată un merge sau un rebase surpriză.

Curățenia în Downloads — obligatorie, nu opțională

Browserul nu suprascrie un fișier existent: salvează al doilea exemplar ca fișier(1).html. Iar cp ~/Downloads/fișier.html ia atunci versiunea veche, în tăcere. Capcana a fost nimerită de trei ori: verifica(1).sh, ghid(1).html, și o dată un ghid vechi reîncărcat în discuție, fără noindex.

# La ÎNCEPUTUL sesiunii — golește Downloads de fișierele proiectului
ls -la ~/Downloads/*.sh ~/Downloads/*.html ~/Downloads/*.patch 2>/dev/null
# te uiți întâi, apoi ștergi explicit, pe nume — niciodată rm orb

# După orice copiere — verifică o linie caracteristică versiunii noi
grep -n "ceva-specific-versiunii-noi" fisier

# La SFÂRȘITUL sesiunii — scoate scripturile one-off din repo
rm -f *.bak *.tmp nume-script.sh

Pentru fișierele primite în discuție, sha256 comparat cu valoarea dată înlocuiește căutarea unei linii caracteristice: dacă hash-ul se potrivește, fișierul e bit cu bit cel testat. Verificarea semnalează singură orice fișier rătăcit în rădăcina unui repo (secțiunea [10]) și orice modificare necomisă (secțiunea [11]).

Mesaje de commit — modelul corect

# ✅ Bun — clar ce s-a schimbat
git commit -m "Add: Corpus IV — Viitorul Europei RO+NO"
git commit -m "Update: index.html — adăugat secțiune Corpus IV"
git commit -m "Fix: link greșit în documentul 3 RO"
git commit -m "Update: sitemap.xml — 48 URL-uri"

# ❌ Rău — nu îți spune nimic peste 3 luni
git commit -m "modificari"
git commit -m "update"

Verificare periodică — o dată pe lună

git log --oneline -10       # Vezi ultimele 10 commit-uri
git status                  # Verifici dacă e ceva necommitat

Din browser: verifici că toate link-urile din index.html funcționează, că sitemap-ul este actualizat și că Google Search Console nu raportează erori.

REGULA SIMPLĂ DE MENȚINERE

git pull înainte să începi. git push după ce termini. Mesaje de commit clare. Sitemap actualizat la fiecare document nou. Aceasta este toată rutina.

CAPITOLUL VIII

Situații de urgență — cum repari

Site-ul nu se actualizează după push

# Forțezi re-deploy-ul cu un commit gol
git commit --allow-empty -m "Force GitHub Pages redeploy"
git push origin main
# Aștepți 3-5 minute, apoi Ctrl+Shift+R în browser

Ai șters din greșeală un fișier

# Vezi în ce commit era fișierul
git log --all --full-history -- fisier-sters.html
# Recuperezi din commit-ul respectiv
git checkout HASH_COMMIT -- fisier-sters.html
git commit -m "Restore: fisier-sters.html"
git push origin main

Ai stricat un fișier și vrei versiunea de ieri

# Vezi istoricul fișierului specific
git log --oneline -- index.html
768cb85 Add Corpus III to main index
b7945a6 Hub principal: index.html
# Restaurezi versiunea anterioară
git checkout 768cb85 -- index.html
git commit -m "Restore: index.html la versiunea 768cb85"
git push origin main

Push-ul e blocat de gardă

Înseamnă că garda și-a făcut treaba. Citește liniile PROBLEMA — fiecare spune ce și unde. Cazurile frecvente:

# "X: N commit(uri) pe GitHub pe care clona nu le are"
git -C ~/X pull origin main

# "X: modificari necomise"
git -C ~/X status --short          # te uiți, apoi comiți sau renunți

# "X: "main" nu are ce cauta in radacina" — fișier-fantomă
ls -la ~/X/main                      # 0 octeți = fantomă; apoi rm ~/X/main

git push --no-verify ocolește garda. E legitim într-un singur caz: când garda însăși greșește — și atunci verificarea se repară în aceeași sesiune, cu un test care arată greșeala. Niciodată pentru „repar mai târziu”.

Repo-ul local și GitHub sunt desincronizate

# Sincronizezi — aduce modificările de pe GitHub
git pull origin main
# Dacă sunt conflicte — git îți arată ce trebuie rezolvat
NICIODATĂ NU FACI ASTA

git push --force — suprascrie istoricul pe GitHub fără posibilitate de recuperare. Nu este niciodată necesar în modelul tău de lucru. Dacă cineva îți sugerează asta — nu face.

CAPITOLUL IX

SEO avansat — fișierele esențiale pe care le are norgedan

Un site cu conținut excelent dar fără infrastructura SEO corectă rămâne invizibil. Acestea sunt fișierele care fac diferența — toate există acum în norgedan.github.io.

robots.txt — harta pentru crawlere

Spune motoarelor de căutare ce pot indexa și unde se află sitemap-ul. Fără el, Google descoperă paginile mai lent și mai incomplet.

User-agent: *
Allow: /

Sitemap: https://norgedan.github.io/sitemap.xml

# Crawlere AI — acces permis pentru indexare si citare
User-agent: GPTBot
Allow: /

User-agent: ClaudeBot
Allow: /

User-agent: PerplexityBot
Allow: /

User-agent: Google-Extended
Allow: /
DE CE PERMITEM CRAWLERELE AI

Pentru documente educative cu date verificate, a fi indexat de ChatGPT, Claude sau Perplexity înseamnă că răspunsurile lor pot cita conținutul tău. Este distribuție gratuită a informației corecte — exact scopul corpusului.

hreflang — cel mai valoros câștig pentru site bilingv

Fiecare document RO are perechea lui NO. Fără hreflang, Google nu știe că sunt versiuni ale aceluiași conținut și le poate trata ca duplicat. Cu hreflang, servește versiunea corectă utilizatorilor din fiecare țară.

<!-- În fiecare document, imediat după canonical -->
<link rel="canonical" href="https://norgedan.github.io/corpus3/ro/2-lumea-in-2026-ro.html">
<link rel="alternate" hreflang="ro" href="https://norgedan.github.io/corpus3/ro/2-lumea-in-2026-ro.html">
<link rel="alternate" hreflang="nb" href="https://norgedan.github.io/corpus3/no/2-verden-i-2026-no.html">
<link rel="alternate" hreflang="x-default" href="https://norgedan.github.io/corpus3/ro/2-lumea-in-2026-ro.html">
REGULA hreflang — RECIPROCITATE OBLIGATORIE

Documentul RO trebuie să declare atât versiunea RO cât și NO. Documentul NO trebuie să declare exact aceleași două. Dacă declarația nu este reciprocă, Google ignoră complet hreflang-ul. x-default indică versiunea implicită pentru utilizatorii din alte țări — la norgedan, româna.

404.html — pagina de eroare proprie

GitHub Pages servește automat 404.html din rădăcina repo-ului când cineva accesează un URL inexistent. Fără el, vizitatorul vede pagina generică GitHub și pleacă. Cu el, vede designul tău și link-uri spre toate corpusurile.

LICENSE — clarifică drepturile

Pentru documente educative, Creative Commons BY 4.0 este alegerea potrivită: oricine poate folosi, redistribui și adapta conținutul, cu condiția atribuirii. Fișierul se numește exact LICENSE, fără extensie — GitHub îl recunoaște automat și îl afișează în interfața repo-ului.

CAPITOLUL X

Note OpenBSD — comenzi specifice

OpenBSD folosește utilitare BSD, nu GNU. Câteva comenzi diferă de exemplele găsite pe internet, care presupun de obicei Linux.

tar — fără --strip-components

# ❌ Nu funcționează pe OpenBSD
tar -xzf arhiva.tar.gz --strip-components=1

# ✅ Varianta corectă — dezarhivezi apoi copiezi
tar -xzf ~/Downloads/arhiva.tar.gz
cp -r optimizari/* .
cp optimizari/.gitignore .   # fișierele ascunse separat
rm -rf optimizari
ATENȚIE LA FIȘIERELE ASCUNSE

cp -r folder/* . nu copiază fișierele care încep cu punct — .gitignore, .htaccess etc. Trebuie copiate explicit, separat.

git pull — configurarea strategiei

Configurarea adoptată pe 27 septembrie, o singură dată, global:

git config --global --unset-all pull.rebase
git config --global pull.ff only
git config --show-origin --get-all pull.rebase   # nu trebuie să mai afișeze nimic

pull.ff only: dacă GitHub are ceva nou, pull-ul doar avansează. Dacă istoriile au divergat, se oprește și te lasă să te uiți — fără merge sau rebase surpriză. Înainte, mașina avea rebase activ, contrar recomandării anterioare din acest ghid (pull.rebase false); a ieșit la iveală când un pull a refuzat să ruleze „with rebase”.

sed — fără \n în textul de înlocuire

BSD sed nu interpretează \n ca linie nouă — îl scrie literal ca litera n. Greșeala aceasta a fost făcută pe 15 septembrie 2026 și a injectat un n rătăcit în status-proiect.html.

# ❌ Merge pe Linux/GNU, strică pe OpenBSD
sed 's|vechi|nou1\nnou2|' fisier

# ✅ Varianta portabilă — backslash urmat de linie nouă reală
sed 's|vechi|nou1\
nou2|' fisier

# ✅ Sau, mai sigur pentru inserții complexe — awk

grep — fără alternanța \|

\| este o extensie GNU. BSD grep o tratează ca text literal, deci pattern-ul nu găsește nimic și eșuează silențios — cel mai periculos tip de eroare. Aceeași sesiune, a doua greșeală de același fel.

# ❌ Nu găsește nimic pe OpenBSD
grep -o 'varianta1\|varianta2' fisier

# ✅ Regex extins POSIX — merge pe ambele
grep -oE 'varianta1|varianta2' fisier

wc -w — numără diferit după locale

Pe text românesc cu diacritice, em-dash-uri și ghilimele „ ", aceeași comandă dă rezultate diferite: 55.931 în locale POSIX, 57.928 în UTF-8. Aproape 2.000 de cuvinte diferență pe același corpus. Fără locale fixat, cifra depinde de sistemul care o măsoară.

# ❌ Rezultatul depinde de mediu
cat *.html | sed 's/<[^>]*>//g' | wc -w

# ✅ Identic pe orice sistem
cat *.html | sed 's/<[^>]*>//g' | LC_ALL=C.UTF-8 wc -w

OpenBSD are C.UTF-8 disponibil — verificabil cu locale -a | grep -i utf.

Conductele pierd contorul — | while read

În shell, o conductă creează un subshell. Orice variabilă modificată înăuntru moare odată cu el:

# ❌ Incrementarea se pierde — contorul rămâne 0
grep ceva fisier | while read -r x; do
  probleme=$((probleme + 1))
done

# ✅ Redirectare dintr-un fișier, fără conductă
grep ceva fisier > /tmp/lista
while read -r x; do
  probleme=$((probleme + 1))
done < /tmp/lista

Bug real: verifica.sh v1 afișa „PROBLEMA ..." și imediat sub ea „totul in regula. Poti face push." Un script de verificare care minte e mai periculos decât lipsa lui.

REGULA GENERALĂ — BSD NU ESTE GNU

Orice exemplu găsit pe internet presupune, de obicei, Linux cu utilitare GNU. Înainte să rulezi un script generat sau copiat, caută în el: \n în sed, \| / \+ / \? în grep, sed -i fără argument, --strip-components, grep -P. Toate acestea se comportă diferit sau eșuează pe OpenBSD.

Lecțiile din 27 septembrie — BSD, POSIX și shell

Fiecare a fost întâlnită efectiv, nu citită undeva.

Litere multibyte între paranteze drepte. [SsȘș] e citit de unele implementări octet cu octet: „Ș” are doi octeți, iar al doilea a fost prins singur (illegal byte sequence). Se folosește alternanța (Ș|ș|S|s) — sau se evită complet regex-ul pe litere.

<( ) nu e POSIX. Substituția de proces e bash. Sub sh dă Syntax error: "(" unexpected. Pentru comparații: fișiere temporare și cmp / diff.

Opțiunile grep înaintea tiparului. GNU grep acceptă grep -E tipar fisier -A1; BSD se oprește la primul argument care nu e opțiune și ia -A1 drept fișier. Întotdeauna: grep -A1 -E tipar fisier.

read cu separator TAB contopește câmpurile goale. TAB e spațiu alb pentru shell: a<TAB><TAB>c devine două câmpuri, nu trei. Niciun câmp gol în datele citite astfel — se pune un marcaj (-).

sha256, nu sha256sum. Pe OpenBSD: sha256 fisier. Afișează hash-ul complet — se compară primele 16 caractere cu valoarea dată.

Niciodată șabloane cu <...> în comenzi. cd ~/<repo> e redirectare pentru shell, nu un loc de completat. Instrucțiunile se dau ca comenzi concrete, gata de rulat.

Nu lipi output în shell. Linia * branch main -> FETCH_HEAD, lipită din greșeală, a creat un fișier gol FETCH_HEAD în rădăcina hub-ului: > e redirectare. Aceeași clasă ca fișierul main din 15 septembrie. Acum verificarea blochează orice fișier neașteptat în rădăcină.

API-ul GitHub întoarce JSON pe o singură linie. Un sed care caută „linia cu description” primește tot fișierul, de câte ori potrivește. Valorile se scot cu grep -o '"description":"[^"]*"'.

Două „Permission denied” diferite. ssh: connect to host github.com port 22: Permission denied = conexiunea nici n-a pornit — firewall-ul local (pf, block return) a refuzat portul 22. Permission denied (publickey) = GitHub a răspuns, dar a refuzat cheia. Soluția pentru prima, fără a slăbi firewall-ul: SSH pe ssh.github.com, portul 443, în ~/.ssh/config. Amprenta serverului se compară întotdeauna cu cea publicată de GitHub înainte de yes.

Fișierele de workflow cer permisiunea workflow pe tokenul PAT (valabil cât timp push-ul mergea prin HTTPS; din 27 sept push-ul merge prin SSH și tokenul a fost șters). Fără ea, GitHub refuză push-ul oricărui fișier din .github/workflows/ — curat, fără să strice nimic. Se adaugă o singură dată, din Settings → Developer settings → Personal access tokens.

Nu lipi mai multe comenzi când una pune întrebări. rm -i a primit ca „răspuns” linia lipită următoare — nu y, deci n-a șters nimic, iar comenzile lipite n-au rulat. O comandă, prompt-ul, apoi următoarea.

wc -w diferă și între implementări, nu doar între locale. busybox numără ca POSIX chiar și în UTF-8. Cifrele de referință sunt cele de pe OpenBSD — identice cu GNU în UTF-8.

Scriptul de verificare pre-push

Principiul „verifică, nu presupune” funcționează doar dacă verificarea se face de fiecare dată — inclusiv când ești obosit, mai ales atunci. De aceea, din 27 septembrie, ea nu mai depinde de nimeni: rulează singură la fiecare push.

scripts/hooks/pre-push — garda. Identică în toate cele 6 repo-uri; verificarea însăși controlează că sunt identice.

Manifestul

7 coloane, niciuna goală, id-uri și fișiere unice.

2
Inventar

Orice .html de pe disc e document din manifest, pagină de structură sau pagină internă (noindex).

Antetul fiecărui document

4
Linkuri și ancore

Toate trimiterile interne ale întregului site, citite din tag-uri reale — un exemplu scris în <pre> sau un comentariu HTML nu mai păcălește verificarea.

5
Hub-ul

Fiecare colecție e prezentată complet: document cu document (toate!) sau prin folder. Linkuirea parțială e semnul documentului uitat.

6
Sitemap-uri

Formulări retrase

Tiparele din scripts/retrase.txt caută în toate paginile publice. Adaugi o linie de fiecare dată când retragi o formulare.

Tag-uri echilibrate; artefactele ">n< ale lui sed BSD.

ADN-ul repo-urilor

README, LICENSE, .gitignore, .nojekyll; rădăcina conține doar ce e permis; garda prezentă, identică și activă; LICENSE = textul oficial CC BY 4.0, identic peste tot; secțiunea de licență identică în toate README-urile; commit-urile se fac cu adresa noreply.

11
Starea git

La push: arbori curați în toate clonele, nimic în urmă față de GitHub; commit-urile nepublicate din alte repo-uri — atenționare.

12
Pagina GitHub

Caseta About a fiecărui repo — descriere, website, topics — comparată prin API cu scripts/about.tsv; Wiki și Projects dezactivate; licența recunoscută. Doar la push și cu --github. Dacă API-ul nu răspunde: atenționare, nu blocaj.

A doua plasă: GitHub Actions

Garda locală vede doar push-urile de pe mașina ta. .github/workflows/verifica.yml — identic în toate cele 6 repo-uri — rulează verifica-site.sh --ci pe serverul GitHub: la fiecare push pe main, în oricare repo; zilnic, doar din hub; și la cerere (Actions → verifica-site → Run workflow). Prinde și ce ocolește garda: o editare făcută direct în browser, o descriere schimbată în About. Un eșec trimite automat email proprietarului contului.

--ci rulează tot, mai puțin ce ține de clona locală (garda activă, identitatea, starea git) — pe server nu există mașina ta. Pagina GitHub se citește cu tokenul automat al Actions, fără limita de 60 de cereri pe oră.

# plus paginile GitHub (rețea)

# doar tabloul
sh ~/norgedan.github.io/scripts/verifica-site.sh --tablou
# la push: automat, prin garda (aduce starea tuturor de pe GitHub)
CUM A FOST VERIFICATĂ VERIFICAREA

Trei medii — non-GNU (dash, one-true-awk, busybox), GNU și OpenBSD — au dat verdicte identice. Douăzeci de defecte introduse intenționat, prinse toate, plus cazuri negative în care scriptul nu are voie să semnaleze nimic. Și dovada inversă: pe un site reparat, iese verde. Un verificator care nu poate trece e la fel de inutil ca unul care trece mereu.

Scripturi versionate vs. scripturi de unică folosință

Distincția contează. .gitignore din corpus este configurat astfel:

# scripturi de lucru locale (one-off, descarcate temporar)
/*.sh
# ...dar scripturile intentionate, versionate, traiesc in scripts/
!scripts/

Merită versionate: scripturi pe care le vei rula din nou — verificări, validări, rapoarte. Nu merită: scripturi de migrare one-off; rezultatul lor e deja în commit-uri.
